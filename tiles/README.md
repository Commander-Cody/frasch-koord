# tiles/

Vector tile build (OpenMapTiles schema → PMTiles) with [Planetiler](https://github.com/onthegomap/planetiler).

- `build.sh <region>` (or `uv run just tiles`) — injects a `name:<tag>` per dialect + the `frasch:*` tags from `names/places.csv`, `names/dialect_areas.geojson`, `names/osm_objects.json` and `names/curation.csv` into the OSM extract, then runs stock Planetiler. Output: `data/<stem>.pmtiles`, which `web/public/tiles/` can link to for the dev server; the website itself ships the published archive (`publish.sh`). The injected extract is `data/<stem>-frasch.osm.pbf`. Add `--bounds=8.3,54.35,8.95,54.8` for a ~1 min Halligen-area test build (but redirect the output, it overwrites the real archive).
  - The archive records what it was built from: `frasch provenance` prints the build's `built_from` stamp (the git blob hashes of those four files and of `names/dialects.csv`, and the extracts the objects were located in), and `build.sh` hands it to Planetiler as `--archive_description`. It is the same stamp `web/public/data/names.json` carries; the frontend warns in the console when the two differ. Planetiler adds the extract's own replication time (`planetiler:osm:osmosisreplicationtime`) by itself.
  - `region` is either a bare file stem, kept meaning `europe/germany/<region>` (e.g. `schleswig-holstein`), or a full Geofabrik path (e.g. `europe/denmark`, `europe/germany/schleswig-holstein`). Either way its last path component is the `<stem>` used for the files in `data/`.
  - The extract is downloaded once, to `data/<stem>-latest.osm.pbf`, and reused after that. Set `REFRESH=1` to force a fresh download (e.g. after Geofabrik's next update).
  - `SNAPSHOT=yymmdd` (six digits, e.g. `SNAPSHOT=260923 uv run just tiles`) builds from the extract Geofabrik dated that day instead: `data/<stem>-260923.osm.pbf`, downloaded from `https://download.geofabrik.de/<path>-260923.osm.pbf` and verified by its `.md5` like the `-latest` file. That is how a build is reproduced from the same extract; nothing else records the snapshot, since Planetiler stamps the extract's replication time into the archive. `just extracts` and the name pipeline stay on `-latest`.
  - Planetiler's global inputs are pinned as well, not fetched by its own `--download`, which takes whatever the upstream URLs serve that day: Natural Earth 5.1.2 (public domain) and the water polygons (osmdata.openstreetmap.de, generated 2026-09-14; ODbL, © OpenStreetMap contributors) come from the `tile-sources-2026-09-30` release of this repository, which mirrors them because upstream has no versioned URL; the lake centerlines are the acalcutt/osm-lakelines `v12` release Planetiler 0.10.2 itself pins. URLs and sha256 are in `build.sh`; the files go to `data/sources/` under the names Planetiler expects, and their paths are passed with `--natural_earth_path`, `--water_polygons_path` and `--lake_centerlines_path`. A file that is missing or does not match its sha256 is downloaded again.
  - Both build outputs (the injected extract and the PMTiles) are written to a temp path first and only `mv`'d into place once complete, so a failed build never disturbs the previous `data/<stem>.pmtiles`; temp files are swept up on any failure.
  - Planetiler itself is pinned to a fixed version (`PLANETILER_VERSION`/`PLANETILER_SHA256` in `build.sh`, 0.10.2) and its jar is verified by sha256, on download and whenever the build starts. A stale/mismatched `tiles/planetiler.jar` is downloaded again rather than silently used.
  - Requires Java 21+ (`JAVA_HOME`, else a JDK under `~/.local/opt/jdk-21*`, else `java` on `PATH`) and the repo's venv (`../.venv`, from `uv sync`, which installs the `frasch` command); both are checked up front with a clear error if missing.
- `fetch.sh` — sourced by `build.sh`, `publish.sh` and `web/scripts/fetch-{tiles,fonts}.sh`: `fetch_verified <url> <dest> <algo> <expected-hash>` downloads to `<dest>.part`, rejects an HTML response (Geofabrik answers a wrong path with one instead of a real 404), verifies the checksum, then `mv`s into place; `fetch_geofabrik_verified <url> <dest>` is the Geofabrik-specific variant that fetches `<url>.md5` and verifies against it; `fetch_pinned <url> <dest> <sha256>` does nothing when `<dest>` already matches the sha256 and otherwise downloads it again with `fetch_verified`. On any failure: non-zero exit, a message on stderr, nothing left behind (no destination, no `.part`). `geofabrik_extract_name` / `geofabrik_extract_url <region> [snapshot]` name the Geofabrik file (`<stem>-latest.osm.pbf`, or `<stem>-<yymmdd>.osm.pbf` with a snapshot) and its URL.
- `publish.sh <region>` (or `uv run just publish-tiles`) — publishes `data/<stem>.pmtiles` for the website: uploads it as the asset of a new GitHub release of this repository, tagged `tiles-<yyyymmdd>-<sha8>` (the first 8 hex digits of its sha256), and rewrites `web/tiles.lock` to pin that URL and sha256. Commit the lock afterwards; `npm run fetch-assets` in `web/` then fetches that archive and `npm run build` ships it (see `web/README.md#tile-hosting`). Needs `gh`, logged in with the right to create releases. Run `just check-tiles` on the archive before publishing it.
- `nametags.sh` — sourced by `build.sh`: `name_tag_options <frasch>` sets Planetiler's `--languages` and `--extra_name_tags` from the `frasch` commands (see *The `frasch:*` tile attributes* below).
- `java.sh` — sourced by `build.sh`: `find_java_home` (the lookup order above) and `java_major`, which reads the major version from both forms of `java -version` (`"17"` for a GA release, `"21.0.2"` for an update), so an older JDK cannot slip past the version check.
- `frasch inject` — the tag injection step (pyosmium). Works with any OSM PBF, so it is independent of the tile tool. `--dry-run` reports what would be tagged and curated without writing. A `places.csv` row whose `osm` is a local reference (`local/<slug>`, for a place OSM does not have) gets its position from the matching `curation.csv` row's `lat`/`lon`: a new node, or — with that row's `polygon_km2` — only a synthetic square, no node. See `names/README.md`.
- `frasch check-tiles <archive.pmtiles>` (or `uv run just check-tiles`) — decodes the z14 tiles around every entry of `names.json` and compares each labelled feature with its search entry: every field of the table of tile keys (`frasch/placenames.py`: kind, dialect, local name, variety, and the German name where the list has one), the name in every dialect of the registry and — for a point that is the object itself — the position. Only the object the entry was placed by is held to that (the first reference of the row's `osm` cell); a row's other objects may lie in another dialect area. The tile build does not run in CI; run this after building tiles. `tiles/tests/test_consistency.py` does the same on a small extract in CI, with the injected extract standing in for the tiles.
- `data/` — downloads and build outputs, not in git. `data/sources/` holds Planetiler's pinned global inputs (Natural Earth, water polygons, lake centerlines; ~1.4 GB, downloaded once).

```
frasch inject <in.osm.pbf> <out.osm.pbf>
              [--names names/places.csv]             the name list
              [--dialects names/dialects.csv]        the registry -> which name:* tags exist
              [--areas names/dialect_areas.geojson]  which dialect is spoken where
              [--objects names/osm_objects.json]     where the name list's objects are
              [--curation names/curation.csv] [--no-curation] [--no-areas]
              [--dry-run]
```

The paths shown are the defaults, the repository's layout whatever the working directory; `build.sh` passes the `NAMES`, `DIALECTS`, `AREAS`, `OBJECTS` and `CURATION` environment variables on only when they are set. There is no `--dialect` switch any more: **every** dialect of the registry is injected in one pass, and the frontend picks one at display time. The dialect areas are optional — without them the injector warns and writes no `frasch:dialect` (and `frasch:local` only where a row has an explicit `local` name, never from OSM's `name:frr`). With them, every object of the name list must be in `--objects` (`uv run just rebuild objects`), or the injector stops and lists the missing ones.

### The `frasch:*` tile attributes

Planetiler runs with `--extra_name_tags=$(frasch tile-keys)`, the attributes of the table below. The stock OpenMapTiles profile passes tags listed there through verbatim, so they arrive as **string** attributes on the labelled `place` features. The names themselves are ordinary `name:*` attributes: one per dialect of `names/dialects.csv` (`--languages=de,da,nds,frr,$(frasch dialects --tags)`), e.g. `name:frr-x-mooring`, `name:frr-x-fering`. Neither list is spelled out in `build.sh`: `nametags.sh` asks the `frasch` commands for both, and the keys themselves are defined once, in `frasch/placenames.py` — a test fails when the injector writes a key Planetiler is not told to carry. The injector also writes the first variant of the row's `de` as `name:de`, in place of OSM's, so the map's German fallback says what the place card does (#61). Where the list has no German name, OSM's `name:de` stays.

| attribute | source | meaning |
|---|---|---|
| `frasch:kind` | `places.csv`'s `kind` column, or `set_tags` in `curation.csv` | `island`, `hallig`, `sand`, `settlement`, `koog`, `harde`, `warft`, `landscape`, `water`, `road`, `country`, `helgoland` — lets the style give a Hallig a different symbol from an island, even though OMT calls both `class=island` |
| `frasch:minzoom` | `curation.csv`'s `minzoom` column | the earliest zoom the label should appear at. **Planetiler does not enforce this** — it is a hint the style must honour, and it can only push a label later, never earlier. |
| `frasch:maxzoom` | `curation.csv`'s `maxzoom` column | the last zoom (inclusive) the label should be shown at. Style-enforced like `frasch:minzoom`. Nordstrand's synthetic island polygon uses it to hand over to the village label at z12. |
| `frasch:dialect` | `names/dialect_areas.geojson` at the object's position in `names/osm_objects.json` (point in polygon, smallest area wins; none for an administrative area above municipality level) | the dialect spoken **where the object is**, e.g. `frr-x-hallig` — not necessarily a dialect the object has a name in. Absent outside the Frisian areas. |
| `frasch:local` | `places.csv`'s `local` column, else the name in `frasch:dialect`'s column, else OSM's `name:frr` inside a dialect area (see below) | what the people of the place themselves call it. This is what the local-dialect view labels with: `coalesce(frasch:local, name:nds, name:latin, name, name:de)` — no `name:frr` in the chain, and `name:de` only as the last resort. An object without a list row can carry it too. |
| `frasch:variety` | the bracket remark on the primary `local` variant | the name of that local variety, e.g. `Foortuftinge` (Fahretoft) or `ååstermooring`. For the UI to show next to the name. |
| `frasch:ref` | the row's `id` | which row of `places.csv` the feature's names come from — `naibel`, `schorkewarw-2`. The same string is the id of the row's entry in the search index, so the frontend can go from a clicked label to the whole name list of that place (the place card). Absent on features that only `curation.csv` touches; a curation row can set it by hand (Nordstrand: `frasch:ref=e-stronj`) when its object belongs to another row — `frasch check-inputs` makes sure it names one. |

#### OSM's Frisian names

OSM's own `name:frr` says nothing about the dialect. Outside the dialect areas it is usually a Frisian exonym (Pinneberg → *Pinebärj*), which the local view must not show. Inside an area of `names/dialect_areas.geojson` it is almost always the form the place itself uses. So there the injector writes it as `frasch:local`, verbatim, wherever the name list gives no local name (#81):

- **An object no row claims**, whatever it is (a Warft, a street, a station): it gets `frasch:local` and nothing else from this rule. Before the main pass the injector scans the extract it is tagging for `name:frr` and locates those objects the way `frasch build objects` locates the list's (a node at its own location, a way or relation inside its polygon, else at its outline point; about 5 s for Schleswig-Holstein). So a new `name:frr` in OSM shows at the next tile build, without a row and without a pipeline step.
- **An object of the name list** whose row has neither a `local` name nor one in the area's dialect: its `name:frr` comes from `names/osm_objects.json` (`name_frr`), the file the search index reads too, so `names.json`'s `local` says the same. An object found only through its row's Wikidata QID is asked itself (a node; a way or relation has no dialect).

A row's own local name always wins. An administrative area above municipality level lies in no dialect area, so its `name:frr` is never a local name. The report counts both kinds.

`curation.csv`'s `polygon_km2` makes the injector add a synthetic `place=island` square around a node (new node and way ids above the extract's highest, written in node/way/relation order so Planetiler's node map stays happy). The square inherits the node's `name` / `name:*` / `frasch:dialect` / `frasch:local` / `frasch:variety` / `frasch:ref`. It exists because OMT labels island *nodes* only from z12 but island *polygons* by area from z8, at the polygon's interior point. For a local reference (a place OSM does not have), the square centres on the curation row's own `lat`/`lon` instead of an OSM node, and no node is written at all. See `names/README.md`.

Anything that has to change how OMT *classifies* a feature (which class, which rank, which minzoom Planetiler picks) must instead be a real OSM tag, written by `curation.csv`'s `set_tags` before Planetiler runs — see `names/README.md`.

Requirements: Java 21+ (`JAVA_HOME`, else a user-local install under `~/.local/opt/jdk-21*`, else `java` on `PATH`), the repo's Python venv (`.venv`, created by `uv sync`, see the root `README.md`). `build.sh` checks both up front and fails with a clear message if either is missing. Memory: `XMX=3g` is enough for Schleswig-Holstein; Germany needs ~8g and a raised WSL memory limit; the planet does not fit on the dev machine (build it on a rented VM with ≥64 GB RAM, then upload the PMTiles).

Planet plan ("the map must never be blank"): one full planet build (~100 GB PMTiles) as the single source; the Frisian name list simply covers only part of it and labels fall back to `name:de` / `name` elsewhere.

## Injector details worth knowing
- Rivers are matched to their `type=waterway` relation, but the OpenMapTiles waterway layer is built from the member ways. The injector reads the relations first and tags every member way that carries the same OSM `name` as the relation (side arms such as "Alte Eider" keep their own name); a member gets the relation's full tag set, dialect area included.
- For the area lookup an object needs a position, and it comes from `names/osm_objects.json`, the file `frasch build objects` writes and the search index reads too (see `names/README.md`, "Where the objects are"). `dialect_areas.dialect_at` asks the dialect areas at the object's point (a node's location; a point *inside* the polygon of a way or relation that closes into one; else the relation's `label` / `admin_centre` member, else a first vertex) and then at its outline point. A vertex alone will not do for a polygon: it lies on the outline of the place, i.e. outside the municipality boundaries the dialect areas are cut from, which is why Amrum (coastline starting 1.6 km south of the Amrum municipalities) and Langeneß used to come out with no dialect at all. The outline stays as a second try for the opposite case, an area that covers only part of an island (Oland): the first point that is in an area at all wins. An administrative boundary above municipality level (Kreis Nordfriesland, an Amt) gets no dialect: it spans several. Objects found only through their Wikidata QID are not in the objects file: a node is asked at its own location, a way or relation gets no `frasch:dialect`.
- An object is labelled from one row: a `places.csv` in which two rows claim the same OSM object or Wikidata item is refused by every command that reads it, the injector included (`frasch check-inputs` lists each such row with its line).
- Every name-list row with a Wikidata QID also tags all place-like OSM objects carrying that QID (a `place`, `boundary`, `natural`, `water` or `waterway` tag, or a waterway relation). This is how the North Sea and Wadden Sea labels (offshore `place=sea` nodes, only present in a planet build) and the place node next to a matched boundary relation get their names. Any other object with the QID is left alone and listed in the report: OSM has a gift shop in Friedrichstadt that carries the town's QID, and its POI label must not turn Frisian ([#55](https://github.com/Commander-Cody/frasch-koord/issues/55)). The row's own `osm` objects are tagged whatever they are.
