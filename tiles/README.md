# tiles/

Vector tile build (OpenMapTiles schema → PMTiles) with [Planetiler](https://github.com/onthegomap/planetiler).

- `build.sh <region>` (or `uv run just tiles`) — injects a `name:<tag>` per dialect + the `frasch:*` tags from `names/places.csv`, `names/dialect_areas.geojson`, `names/osm_objects.json` and `names/curation.csv` into the OSM extract, then runs stock Planetiler. Output: `data/<stem>.pmtiles`, which it then links from `web/public/tiles/` for the dev server when its name is the one `web/tiles.lock` pins (`devlink.sh`; `uv run just setup` links the published archive again); the website itself ships the published archive (`publish.sh`). The injected extract is `data/<stem>-frasch.osm.pbf`. Add `--bounds=8.3,54.35,8.95,54.8` for a ~1 min Halligen-area test build (but redirect the output, it overwrites the real archive).
  - The archive records what it was built from: `frasch provenance` prints the build's `built_from` stamp (the git blob hashes of those four files and of `names/dialects.csv`, and the extracts the objects were located in), and `build.sh` hands it to Planetiler as `--archive_description`. It is the same stamp `web/public/data/names.json` carries; the site's build warns when the two differ (`web/vite-plugins/build/provenance.ts`). Planetiler adds the extract's own replication time (`planetiler:osm:osmosisreplicationtime`) by itself.
  - The OpenMapTiles layers `housenumber` and `mountain_peak` are left out (`--exclude_layers`): no layer of `web/src/map/style/frasch-bright.json` reads them (#112). A style layer for one of them has to take it off that list.
  - `region` is either a bare file stem, kept meaning `europe/germany/<region>` (e.g. `schleswig-holstein`), or a full Geofabrik path (e.g. `europe/denmark`, `europe/germany/schleswig-holstein`). Either way its last path component is the `<stem>` used for the files in `data/`.
  - The extract is downloaded once, to `data/<stem>-latest.osm.pbf`, and reused after that. Set `REFRESH=1` to force a fresh download (e.g. after Geofabrik's next update).
  - `SNAPSHOT=yymmdd` (six digits, e.g. `SNAPSHOT=260923 uv run just tiles`) builds from the extract Geofabrik dated that day instead: `data/<stem>-260923.osm.pbf`, downloaded from `https://download.geofabrik.de/<path>-260923.osm.pbf` and verified by its `.md5` like the `-latest` file. That is how a build is reproduced from the same extract; nothing else records the snapshot, since Planetiler stamps the extract's replication time into the archive. `just extracts` and the name pipeline stay on `-latest`.
  - Planetiler's global inputs are pinned as well, not fetched by its own `--download`, which takes whatever the upstream URLs serve that day: Natural Earth 5.1.2 (public domain) and the water polygons (osmdata.openstreetmap.de, generated 2026-09-14; ODbL, © OpenStreetMap contributors) come from the `tile-sources-2026-09-30` release of this repository, which mirrors them because upstream has no versioned URL; the lake centerlines are the acalcutt/osm-lakelines `v12` release Planetiler 0.10.2 itself pins. URLs and sha256 are in `sources.lock`; the files go to `data/sources/` under the names Planetiler expects, and their paths are passed with `--natural_earth_path`, `--water_polygons_path` and `--lake_centerlines_path`. A file that is missing or does not match its sha256 is downloaded again.
  - Both build outputs (the injected extract and the PMTiles) are written to a temp path first and only `mv`'d into place once complete, so a failed build never disturbs the previous `data/<stem>.pmtiles`; temp files are swept up on any failure.
  - Planetiler itself is pinned to a fixed version (`PLANETILER_URL`/`PLANETILER_SHA256` in `sources.lock`, 0.10.2) and its jar is verified by sha256, on download and whenever the build starts. A stale/mismatched `tiles/planetiler.jar` is downloaded again rather than silently used.
  - Requires Java 21+ (`JAVA_HOME`, else a JDK under `~/.local/opt/jdk-21*`, else `java` on `PATH`) and the repo's venv (`../.venv`, from `uv sync`, which installs the `frasch` command); both are checked up front with a clear error if missing.
- `fetch.sh` — the download core, sourced by `build.sh` and `geofabrik.sh`: `fetch_verified <url> <dest> <algo> <expected-hash>` downloads to `<dest>.part`, rejects an HTML response (Geofabrik answers a wrong path with one instead of a real 404), verifies the checksum, then `mv`s into place; `fetch_pinned <url> <dest> <sha256>` does nothing when `<dest>` already matches the sha256 and otherwise downloads it again with `fetch_verified`; `fetch_text <url>` prints a small text file such as a checksum sidecar; `checksum_of <algo> <file>` prints a file's sha256 or md5. On any failure: non-zero exit, a message on stderr, nothing left behind (no destination, no `.part`).
- `geofabrik.sh` — Geofabrik's extracts, sourced by `build.sh`, `publish.sh` and `just extracts`: `geofabrik_path` / `region_stem <region>` validate a region and name its stem; `geofabrik_extract_name` / `geofabrik_extract_url <region> [snapshot]` name the Geofabrik file (`<stem>-latest.osm.pbf`, or `<stem>-<yymmdd>.osm.pbf` with a snapshot) and its URL; `fetch_geofabrik_verified <url> <dest>` downloads one and verifies it against Geofabrik's `<url>.md5`; `fetch_geofabrik_extract <region> <dir> [snapshot]` puts a region's extract into `<dir>` unless it is there already (or `REFRESH=1` is set). `GEOFABRIK_URL` names another server than `https://download.geofabrik.de`, as the tests do.
- `publish.sh <region>` (or `uv run just publish-tiles`) — publishes `data/<stem>.pmtiles` for the website: uploads it as the asset of a new GitHub release of this repository, tagged `tiles-<yyyymmdd>-<sha8>` (the first 8 hex digits of its sha256), and rewrites the `ARCHIVE_URL` and `ARCHIVE_SHA256` lines of `web/tiles.lock` to pin that URL and sha256; the site serves the archive under the asset's name, `<stem>.pmtiles`. Commit the lock afterwards; `npm run fetch-assets` in `web/` then fetches that archive and `npm run build` ships it (see `web/README.md#tile-hosting`). Needs `gh`, logged in with the right to create releases. `just publish-tiles` runs `just check-tiles` on the archive first and publishes nothing when it fails.
- `sources.lock` — what `build.sh` builds with besides the extract, each a `<NAME>_URL` and `<NAME>_SHA256` line: Planetiler and its global inputs.
- `devlink.sh` — `link_dev_archive <tiles.lock> <link dir> <archive>`, sourced by `build.sh`: links `<link dir>/<pinned name>` to the archive when its file name is the pinned one, and otherwise says why it links nothing.
- `lock.sh` — the lock files' `KEY=value` lines (`sources.lock`, `web/tiles.lock`), sourced by `build.sh` and `publish.sh`: `lock_get <file> <key>` prints a value; `lock_set <file> <key> <value>` rewrites that one line and nothing else of the file. Either fails on a file without the key.
- `nametags.sh` — sourced by `build.sh`: `name_tag_options <frasch>` sets Planetiler's `--languages` and `--extra_name_tags` from the `frasch` commands (see *The `frasch:*` tile attributes* below).
- `java.sh` — sourced by `build.sh`: `find_java_home` (the lookup order above) and `java_major`, which reads the major version from both forms of `java -version` (`"17"` for a GA release, `"21.0.2"` for an update), so an older JDK cannot slip past the version check.
- `frasch inject` — the tag injection step (pyosmium). Works with any OSM PBF, so it is independent of the tile tool. `--dry-run` reports what would be tagged and curated without writing. A `places.csv` row whose `osm` is a local reference (`local/<slug>`, for a place OSM does not have) gets its position from the matching `curation.csv` row's `lat`/`lon`: a new node, or — with that row's `polygon_km2` — only a synthetic square, no node. See `names/README.md`.
- `frasch check-tiles <archive.pmtiles>` (or `uv run just check-tiles`) — decodes the z14 tiles around every entry of `names.json` and compares each labelled feature with its search entry: every field of the table of tile keys (`frasch/placenames.py`: kind, dialect, local name, variety, and the German name where the list has one), the name in every dialect of the registry and — for a point that is the object itself — the position. Only the object the entry was placed by is held to that (the first reference of the row's `osm` cell); a row's other objects may lie in another dialect area. The tile build does not run in CI; run this after building tiles. `tiles/tests/test_consistency.py` does the same on a small extract in CI, with the injected extract standing in for the tiles. It also checks `web/src/testing/generated/listedScenarios.json`, the committed record of what the entry and the injected object of each of the place card's listed scenarios say, which `web/src/mapCardConsistency.test.ts` checks the card and the map label against: the test fails when the file is no longer what the pipeline gives, and `uv run pytest tiles/tests/test_consistency.py --write-scenarios` rewrites it.
- `data/` — downloads and build outputs, not in git. `data/sources/` holds Planetiler's pinned global inputs (Natural Earth, water polygons, lake centerlines; ~1.4 GB, downloaded once).

```
frasch inject <in.osm.pbf> <out.osm.pbf>
              [--names names/places.csv]             the name list
              [--dialects names/dialects.csv]        the registry -> which name:* tags exist
              [--areas names/dialect_areas.geojson]  which dialect is spoken where
              [--objects names/osm_objects.json]     where the name list's objects are
              [--curation names/curation.csv]        the map curation
              [--dry-run]
```

The paths shown are the defaults, the repository's layout whatever the working directory; `build.sh` passes the `NAMES`, `DIALECTS`, `AREAS`, `OBJECTS` and `CURATION` environment variables on only when they are set. There is no `--dialect` switch any more: **every** dialect of the registry is injected in one pass, and the frontend picks one at display time. All five files are required: the injector stops before it reads the extract when one is missing, and names it (a tile build without dialect areas is not wanted, and `frasch provenance` could not stamp it). Every object of the name list must be in `--objects` (`uv run just rebuild objects`), or the injector stops and lists the missing ones. `build.sh` asks `frasch provenance` for the build's stamp before it injects, so a missing file ends the build at once and not after the minutes of injecting.

### The `frasch:*` tile attributes

Planetiler runs with `--extra_name_tags=$(frasch tile-keys)`, the attributes of the table below. The stock OpenMapTiles profile passes tags listed there through verbatim, so they arrive as **string** attributes on the labelled `place` features. The names themselves are ordinary `name:*` attributes: German, Danish, OSM's own Frisian, and one per variety of `names/dialects.csv` (`--languages=de,da,frr,$(frasch dialects --tags)`), e.g. `name:frr-x-mooring`, `name:frr-x-fering`, `name:nds`, `name:jut`. Low Saxon is a variety of the registry and OSM's language at once, so it is listed once: the list's `nds` replaces OSM's `name:nds` on the row's objects, and OSM's stays where the list has none — the same rule as for `name:de`. Neither list is spelled out in `build.sh`: `nametags.sh` asks the `frasch` commands for both, and the keys themselves are defined once, in `frasch/placenames.py` — a test fails when the injector writes a key Planetiler is not told to carry. The injector also writes the first variant of the row's `de` as `name:de`, in place of OSM's, so the map's German fallback says what the place card does (#61). Where the list has no German name, OSM's `name:de` stays.

| attribute | source | meaning |
|---|---|---|
| `frasch:kind` | `places.csv`'s `kind` column, or `set_tags` in `curation.csv` | `island`, `hallig`, `sand`, `settlement`, `koog`, `harde`, `warft`, `landscape`, `water`, `road`, `country`, `helgoland` — lets the style give a Hallig a different symbol from an island, even though OMT calls both `class=island` |
| `frasch:minzoom` | `curation.csv`'s `minzoom` column | the earliest zoom the label should appear at. **Planetiler does not enforce this** — it is a hint the style must honour, and it can only push a label later, never earlier. |
| `frasch:maxzoom` | `curation.csv`'s `maxzoom` column | the last zoom (inclusive) the label should be shown at. Style-enforced like `frasch:minzoom`. Nordstrand's synthetic island polygon uses it to hand over to the village label at z12. |
| `frasch:dialect` | `names/dialect_areas.geojson` at the object's position in `names/osm_objects.json` — for a way or relation with a square, at its centre, the curation row's `lat`/`lon` (point in polygon, smallest area wins; none for an administrative area above municipality level) | the dialect spoken **where the object is**, e.g. `frr-x-hallig` — not necessarily a dialect the object has a name in: a Frisian dialect, or `jut` in a Synnejysk area. Absent outside every area (Low Saxon by default). The Frisian views read it: their chain differs inside a Frisian area (`web/README.md`). |
| `frasch:local` | `places.csv`'s `local` column, else the name in `frasch:dialect`'s column, else OSM's name in the area's language inside an area: `name:frr` in a Frisian one, `name:nds` in a Low Saxon one, none in a Synnejysk one (see below) | what the people of the place themselves call it — a Frisian, Synnejysk or Low Saxon name. This is what the local-dialect view labels with: `coalesce(frasch:local, name:nds, name:latin, name, name:de)` — no `name:frr` in the chain, and `name:de` only as the last resort. A Frisian view reads it right after its own dialect in a Frisian area, and after `name:frr` anywhere else (`web/README.md`). An object without a list row can carry it too. |
| `frasch:variety` | the bracket remark on the primary `local` variant | the name of that local variety, e.g. `Foortuftinge` (Fahretoft) or `ååstermooring`. For the UI to show next to the name. |
| `frasch:square` | the injector, on a synthetic square | `yes`: the label comes from a synthetic square of `curation.csv` (see below), not from an OSM polygon. `frasch check-tiles` compares such a label with its row's search entry, position included. |
| `frasch:ref` | the row's `id` | which row of `places.csv` the feature's names come from — `naibel`, `schorkewarw-2`. The same string is the id of the row's entry in the search index, so the frontend can go from a clicked label to the whole name list of that place (the place card). Absent on features that only `curation.csv` touches; a curation row can set it by hand (Nordstrand: `frasch:ref=e-stronj`) when its object belongs to another row — `frasch check-inputs` makes sure it names one. |

#### OSM's Frisian names

OSM's own `name:frr` says nothing about the dialect. Outside the Frisian dialect areas it is usually a Frisian exonym (Pinneberg → *Pinebärj*, and in a Synnejysk area too), which the local view must not show. Inside a Frisian area of `names/dialect_areas.geojson` it is almost always the form the place itself uses. So there the injector writes it as `frasch:local`, verbatim, wherever the name list gives no local name (#81; in an explicit Low Saxon area OSM's `name:nds` is the local name instead, and the local view's next step anyway):

- **An object no row claims**, whatever it is (a Warft, a street, a station): it gets `frasch:local` and its area's `frasch:dialect`, nothing else from this rule — the area so that a Frisian view's chain treats it as lying in a Frisian area, as it does a listed place. Before the main pass the injector scans the extract it is tagging for `name:frr` and locates those objects (but for the ones a row holds by reference, which the objects file has) the way `frasch build objects` locates the list's (a node at its own location, a way or relation inside its polygon, else at its outline point; about 5 s for Schleswig-Holstein). So a new `name:frr` in OSM shows at the next tile build, without a row and without a pipeline step.
- **An object of the name list** whose row has neither a `local` name nor one in the area's dialect: its `name:frr` comes from `names/osm_objects.json` (`name_frr`), the file the search index reads too, so `names.json`'s `local` says the same. An object found only through its row's Wikidata QID is asked itself (a node; a way or relation has no dialect).

A row's own local name always wins. An administrative area above municipality level lies in no dialect area, so its `name:frr` is never a local name. Neither is it in a Synnejysk area: OSM has no `name:jut`, so there only the list gives a local name. The report counts both kinds.

`curation.csv`'s `polygon_km2` makes the injector add a synthetic `place=island` square for one object (new node and way ids above the extract's highest, written in node/way/relation order so Planetiler's node map stays happy). One rule holds for every square: it belongs to the **row's own object**; it is centred on that object if it is a node, else on the curation row's `lat`/`lon`; it **replaces the object's own place label** (the injector drops the object's `place` tag and leaves all its others, `natural=coastline` included — `place=island` feeds nothing but the place layer); and the row's position — its search entry, its `frasch:dialect`, what `frasch check-tiles` compares — is the square's centre. The square inherits the object's `name` / `name:*` / `frasch:dialect` / `frasch:local` / `frasch:variety` / `frasch:ref`, gets the curation row's `set_tags` / zooms (`frasch:kind` among them), and carries `frasch:square=yes`, by which `frasch check-tiles` holds its label to its row's entry: the square's way id is the injector's, not the object's. The square of a way or relation is written before the first way, so a pre-pass reads those objects' tags first. Squares exist because OMT labels island *nodes* only from z12 but island *polygons* by area from z8, at the polygon's interior point — which for an island polygon that also covers foreshore can lie off the island (Oland: its coastline way includes the accretion fields along the rail dam, so its interior point lay outside the Sommerdeich; its square sits on the middle of the Hallig at the coastline polygon's own 2.1 km², so rank and first zoom stay). For a local reference (a place OSM does not have), the square centres on the curation row's own `lat`/`lon`, and no node is written at all. See `names/README.md`.

Anything that has to change how OMT *classifies* a feature (which class, which rank, which minzoom Planetiler picks) must instead be a real OSM tag, written by `curation.csv`'s `set_tags` before Planetiler runs — see `names/README.md`.

Requirements: Java 21+ (`JAVA_HOME`, else a user-local install under `~/.local/opt/jdk-21*`, else `java` on `PATH`), the repo's Python venv (`.venv`, created by `uv sync`, see the root `README.md`). `build.sh` checks both up front and fails with a clear message if either is missing. Memory: `XMX=3g` is enough for Schleswig-Holstein; Germany needs ~8g and a raised WSL memory limit; the planet does not fit on the dev machine (build it on a rented VM with ≥64 GB RAM, then upload the PMTiles).

Planet plan ("the map must never be blank"): one full planet build (~100 GB PMTiles) as the single source; the Frisian name list simply covers only part of it and labels fall back to `name:de` / `name` elsewhere.

## Injector details worth knowing
- Objects are matched by their reference or their Wikidata QID only; no name matching happens in the injector, so the hand-reviewed decisions in the CSVs are the single source of truth. All other tags of a matched object are preserved, as are all objects no file mentions.
- The command prints its report when the run is done: what the inputs hold, then what the scan tagged, added and curated and what it did not find. Every object in it is written as the lists spell it (`node/1`, `way/2`, `relation/3`). The code is `frasch/inject_names.py` (the command and the `Injector`) and the package `frasch/inject/` (see `names/README.md#code`).
- Rivers are matched to their `type=waterway` relation, but the OpenMapTiles waterway layer is built from the member ways. The injector reads the relations first and tags every member way that carries the same OSM `name` as the relation (side arms such as "Alte Eider" keep their own name); a member gets the relation's full tag set, dialect area included.
- For the area lookup an object needs a position, and it comes from `names/osm_objects.json`, the file `frasch build objects` writes and the search index reads too (see `names/README.md`, "Where the objects are"). `dialect_areas.dialect_at` asks the dialect areas at the object's point (a node's location; a point *inside* the polygon of a way or relation that closes into one; else the relation's `label` / `admin_centre` member, else a first vertex) and then at its outline point. A vertex alone will not do for a polygon: it lies on the outline of the place, i.e. outside the municipality boundaries the dialect areas are cut from, which is why Amrum (coastline starting 1.6 km south of the Amrum municipalities) and Langeneß used to come out with no dialect at all. The outline stays as a second try for the opposite case, an area that covers only part of an island: the first point that is in an area at all wins. A way or relation with a curation square is asked at the square's centre alone, where its label and its search entry are (Oland, which needed the outline before, lies in the Hallig area there). An administrative boundary above municipality level (Kreis Nordfriesland, an Amt) gets no dialect: it spans several. Objects found only through their Wikidata QID are not in the objects file: a node is asked at its own location, a way or relation gets no `frasch:dialect`.
- An object is labelled from one row: a `places.csv` in which two rows claim the same OSM object or Wikidata item is refused by every command that reads it, the injector included (`frasch check-inputs` lists each such row with its line).
- Every name-list row with a Wikidata QID also tags all place-like OSM objects carrying that QID (a `place`, `boundary`, `natural`, `water` or `waterway` tag, or a waterway relation). This is how the North Sea and Wadden Sea labels (offshore `place=sea` nodes, only present in a planet build) and the place node next to a matched boundary relation get their names. Any other object with the QID is left alone and listed in the report: OSM has a gift shop in Friedrichstadt that carries the town's QID, and its POI label must not turn Frisian ([#55](https://github.com/Commander-Cody/frasch-koord/issues/55)). The row's own `osm` objects are tagged whatever they are.
